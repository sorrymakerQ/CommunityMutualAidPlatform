## 一、简历正文（可直接粘贴）

### 社区邻里互助平台 ｜ 独立开发（个人项目 / 毕业设计）

**技术栈**：Spring Boot 2.7 · MyBatis · MySQL 8 · Redis · Redisson · RocketMQ · Sa-Token · 支付宝开放平台 · 阿里云 OSS · Vue 3 + TypeScript + Vite

**项目简介**：面向社区场景的互助悬赏平台。发布者悬赏发布求助并完成支付，邻里接单提供帮助，完成后双向评价并结算信用分。独立完成数据库设计、后端接口与前端页面，覆盖**用户/求助/支付/订单/评价**完整业务闭环。

**核心工作**：

1. **并发接单防超卖**：同一求助的并发接单用 **Redisson 分布式锁**串行化，并以数据库唯一键 `uk_help_helper_seq(help_id, helper_id, seq)` 作为最终正确性兜底，配合 `accepted_num < helper_num` 的 CAS 更新防止名额超额。设计上区分职责——**锁解决性能（避免大量冲突重试），唯一键保证正确性（锁超时/GC 停顿失效时数据依然正确）**。

2. **支付宝支付集成**：基于支付宝沙箱实现收银台支付，以商户支付单号 `pay_no` 作 `out_trade_no` 关联回调；异步通知做**三重校验**（RSA2 验签 + 回调金额比对 + 卖家账号比对）抵御伪造通知；状态流转用 CAS 保证幂等——`UPDATE tb_pay_order SET status=1, channel=?, pay_time=NOW() WHERE help_id=? AND status=0`，重复通知命中 0 行直接应答 success。

3. **RocketMQ 延迟消息实现支付超时关单**：发布求助时投递 30 分钟延迟消息（延迟等级 16），到点用**双状态机 CAS**（求助与支付单同时处于"待支付"才取消），替代定时任务全表扫描；通知走 MQ 异步解耦，并按"MQ 不可用不影响接单主流程"做降级，保证核心链路可用性。

4. **二级缓存与缓存三大问题治理**：设计 `MultiLevelCache`（Caffeine L1 → Redis L2 → MySQL L3）逐级回源与回填，L1 设 30 秒短 TTL 使实例间不一致窗口有上限；针对缓存三大经典问题分别落地——**空值哨兵防穿透**（DB 确认不存在时写入空串标记，因缓存值均为对象 JSON 序列化结果、不可能得到空串，可安全区分"未缓存"与"缓存了不存在"）、**SETNX 互斥锁防击穿**（仅持锁线程回源 DB，其余线程有界等待后重读缓存，仍未命中才自行兜底查库）、**TTL 随机抖动防雪崩**（写入时叠加 0~20% 随机增量，打散批量写入的集中过期）。

5. **RBAC 鉴权与幂等**：基于 Sa-Token 实现用户-角色-权限三级模型，权限码语义化（`help:publish`、`order:accept`、`user:manage` 等）并以注解鉴权，实现**接口声明能力、授权由配置决定**的解耦；用户信息托管在 Sa-Token 的 Account-Session 而非自建缓存，避免会话与缓存双份状态不一致；写接口引入 `X-Request-Id` + Redis `SETNX` 幂等键，杜绝双击与网络重试导致的重复提交。

6. **状态审计与信用分体系**：订单状态每次流转落审计表（操作人 / 前后状态 / 原因），支持问题追溯；信用分采用「当前值 + 流水」双表设计并配乐观锁 `version` 防并发丢分，支持对账。

7. **慢查询治理**：分析 7 天 1800+ 条慢查询日志，按「累计耗时占比」而非「单条最慢」定位真问题，识别出深分页与缺失复合索引，为求助表建立 `(status, is_deleted, create_time, category_id)` 联合索引。

## 二、面试自述（30 秒版）

> 这是一个社区互助悬赏平台，业务闭环是「发布求助 → 支付 → 邻里接单 → 履约 → 双向评价」。
>
> 我重点做了两块：**支付**和**并发接单**——这两个是最容易出错的场景。
>
> 支付上我做了三重校验防伪造通知，状态流转用 CAS 保证幂等，重复通知不会重复处理；超时关单没走定时任务，而是用 RocketMQ 的延迟消息做事件驱动。
>
> 接单上我用了分布式锁 + 数据库唯一键 + 名额 CAS 三层防护，设计思路是**锁负责性能、唯一键负责正确性**。
>
> 缓存上我做了二级缓存（Caffeine + Redis），并针对穿透、击穿、雪崩分别落地了空值哨兵、互斥锁和 TTL 抖动。
>
> 另外我也做了一轮慢查询治理，通过分析慢日志发现真问题是深分页而不是单条慢 SQL。

## 三、高频追问预案

### Q1：为什么加了分布式锁还要唯一键？（★最高频）

**答**：因为**锁不是正确性保证**。Redisson 锁会超时、会因 JVM GC 停顿导致续期失败、Redis 主从切换时会丢锁。所以正确的分层是：

- **锁**：解决性能问题，让并发请求串行化，避免大量冲突重试
- **唯一键**：解决正确性问题，锁失效时数据库依然拒绝重复插入

再加 `accepted_num < helper_num` 的 CAS 防超额。三层各司其职。

### Q2：异步通知怎么保证幂等？怎么防伪造？

**答**：防伪造靠**三重校验**——RSA2 验签（支付宝公钥）、回调金额必须等于本地支付单金额、卖家 ID 必须匹配（防止别人拿你的 appId 伪造）。

幂等靠 **CAS**：`UPDATE ... WHERE help_id=? AND status=0`，只有把行从 0 改成 1 的那个请求返回 1，重复通知返回 0。

> 追问「为什么不先查后判断再更新」→ 先查后更新有并发窗口，两个请求可能都查到 status=0；CAS 把判断和更新合并成一条原子 SQL，由数据库行锁裁决。

### Q3：`out_trade_no` 和 `trade_no` 有什么区别？

**答**：`out_trade_no` 是**商户订单号**（我生成的 `pay_no`），`trade_no` 是**支付宝交易号**。下单时传 `out_trade_no`，回调里两个都会带回来。**退款优先用 `out_trade_no`**，因为它是我自己的号，不依赖回调是否成功落库。

### Q4：为什么用 MQ 不用定时任务做超时关单？

**答**：定时任务要周期性全表扫描待支付订单，数据量大时扫描成本高且不精准（最坏要等一个扫描周期）。RocketMQ 延迟消息是**事件驱动**——发布求助时投递一条，精确在 30 分钟后触发单条检查，DB 压力接近 0。

**局限**：RocketMQ 内置延迟只支持固定的 18 个等级、最大 2 小时，所以更长的延迟（比如订单 1 天超时）还是得靠定时扫描。

### Q5：为什么用二级缓存？L1 和 Redis 不一致怎么办？

**答**：L1 Caffeine 在进程内，读取约 100 纳秒，省掉 Redis 的网络往返（约 1 毫秒），适合极热数据；L2 Redis 跨实例共享。

**不一致确实无法消除**——L1 在各 JVM 内存里，无法与 Redis 同事务。所以我的设计不是消除不一致，而是**给不一致设上限**：写路径同步失效本实例 L1 + L2，L1 再设 30 秒短 TTL 兜底，最坏情况脏数据窗口 ≤ 30 秒。

**★ 追问「缓存三大问题怎么解决的」（高频）**：

- **穿透**：空值哨兵。DB 确认不存在时写入空串标记（TTL 60 秒），期间请求在 L1/L2 就被拦截。**为什么用空串**——缓存值都是对象的 JSON 序列化结果，JSON 序列化一个对象永远不可能得到空串，所以空串可以安全地区分"没缓存"和"缓存了不存在"，这是防穿透实现里最容易搞错的地方。
- **击穿**：SETNX 互斥锁，只有抢到锁的线程回源 DB。**这里我踩过一个坑**：一开始没抢到锁的线程直接返回 null，结果调用方分不清"数据不存在"和"没抢到锁"，会把真实存在的求助误判成"已删除"。后来改成**有界等待**——等待 3×30ms 后重读缓存，仍未命中才自己查库兜底，保证 **null 语义唯一**。
- **雪崩**：TTL 随机抖动，写入时在基础 TTL 上叠加 0~20% 随机增量，打散批量写入（比如缓存预热）的集中过期时间。

> 追问「多实例的 L1 怎么办」→ 诚实答：当前是单实例部署。多实例常见方案是用 Redis Pub/Sub 广播失效（A 实例改数据后通知 B/C 清各自 L1），我评估后**没做**——因为 L1 已有 30 秒 TTL 兜底，不一致窗口本来就有上限，而 Pub/Sub 是「即发即弃」的、丢消息还是得靠 TTL 收敛，收益不明显。这是我权衡后的取舍。

**★ 这个回答很关键**：它把「我没做」变成了「我评估后决定不做，理由是……」，比硬说有更好。

### Q6：为什么权限码不用角色注解？

**答**：因为**同一能力常被多个角色共享**。我项目里 6 个权限有 3 个是 admin 和 user 都有的，如果直接用 `@SaCheckRole` 就得写 `{"admin","user"}` 这种，而且**每新增一个角色都必须改代码**。用权限码后，接口只声明"我需要什么能力"，"谁能做"是数据库里配的，**加角色不用改代码**。

至于为什么还需要角色——用户量到百万级不可能逐个配权限，**角色是权限的批量打包**。本质是：权限是元素，角色是集合。

### Q7：慢查询治理你怎么做的？

**答**：关键认知是**要看累计耗时占比，不是单条最慢**。我分析 1800 多条慢日志时发现，单条最慢的 534 秒是造数脚本的一次性语句，没有参考价值；真正的元凶是 `LIMIT offset, size` 的深分页——单条才 9 秒，但重复了近千次，占总耗时 60%。

> 追问「怎么解决的」→ ⚠️ **如实说**：定位到了但还没改完。深分页的正确解法是游标分页（用 `(create_time, id) < (?, ?)` 代替 offset），但我发现写成行构造器时 MySQL 不走索引会退化成全表扫描，需要改写成 `create_time < ? OR (create_time = ? AND id < ?)` 才能命中索引。这是我下一步要做的。

## 六、一句话定位

别写「实现了支付功能」（人人都写），写：

> **在高并发接单和支付这两个最容易出错的场景上做了分层防护设计——锁 + 唯一键保证不超卖，验签 + 三重校验 + CAS 保证不重复扣款。**

关键在于**「防护」**和**「保证」**这两个词——它们暗示你想过失败路径，这是初级和中级开发的分水岭。
